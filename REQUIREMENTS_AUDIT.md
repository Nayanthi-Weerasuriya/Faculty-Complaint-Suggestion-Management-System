The project is **not yet a claim of complete proposal compliance or production readiness**: reporting gaps and operational work remain below. At the user's request, these findings were recorded without implementing new features or changing the chosen UI.

## Findings left unchanged, with suggested implementation

### 1. Management chart bars use fixed percentages

`templates/dashboard/management_dashboard.html` renders complaint/suggestion bars at 60/40 and urgent/normal bars at 15/85 regardless of the real counts. Text counts are dynamic, so the graphics can contradict them.

Suggested work: derive percentage widths from the same filtered queryset, handle zero totals, provide accessible labels and test uneven/empty datasets. This is a reporting defect, not an unused decoration to delete silently.

### 2. Required status summaries are not all directly visible

See criterion 19. The missing boxes were user-requested removals, so they were not restored during cleanup.

Suggested work: agree on a compact summary row, text list or report summary that provides the required counts while keeping the five-card coordinator layout and uncluttered management dashboard.

### 3. Coordinator date-range filtering has no visible controls

`dashboard/views.py` accepts date_from/date_to, but `templates/dashboard/admin_dashboard.html` does not expose those inputs. Management date controls are present.

Suggested work: add two date controls to the coordinator form with clear validation feedback and preserve them through the existing card filters.

### 4. Pending-authority table needs a consistent definition

`dashboard/views.py` includes every authority, including inactive zero-pending units. Its assigned/pending count excludes final statuses, while its average-age queryset includes only Assigned/Not Started/In Progress/Waiting for Information. Under Review/Reopened records can therefore contribute to one number and not the other. A closed historical Dean's Office case does not mean the Dean currently has pending work.

Suggested work: choose one pending-state definition for all columns and averages; hide zero-pending rows from the pending table while retaining historical cases in detailed reports.

### 5. Real email and scheduled operations are not connected

The current console backend does not deliver verification, password-reset or notification emails to inboxes. The local verification button is an intentional demo aid for a newly registered account in its own browser session, and is hidden with SMTP/production/nonlocal hosts. Pending reminder and database-plus-media backup commands exist, but have not been installed as daily scheduled jobs.

Suggested work before live use: approved sender/SMTP, a real delivered-email test, daily scheduling, secure backup retention and a documented restore exercise. These require hosting/university configuration, not invented credentials.

### 6. Direct Django administration can bypass the portal workflow

`cases/admin.py` permits direct case/comment edits. Those saves are not routed through the portal views that create business audit records, set workflow timestamps and send notifications. The normal portal workflow is tested, but an administrative status change can miss those side effects. The audit admin also does not explicitly disable deletion.

Suggested work: make case/audit administration read-only where appropriate, or centralize workflow mutations in a service called by both interfaces. Test solved-notification, timestamp and audit behavior through the admin path as well.

### 7. Assignment does not require a usable handler account

The form checks whether an authority is active, but not whether it has an active Authority-role user. Creating an authority does not create a login account. An administrator can therefore configure an active unit without someone able to handle its queue. Current three active demo units do have accounts.

Suggested work: add a warning or validation for missing handlers and a clear user-provisioning checklist. Accounts should remain explicitly created by the System Administrator.

### 8. Definitions and robustness to confirm

- `Case.is_open` means active work and excludes solved/closed/rejected, whereas the proposal defines open as not closed. The open filter follows the proposal's broader meaning. Use separate names for active work and proposal-open reporting to avoid future confusion.
- Average resolution days currently averages completed whole days, losing partial-day precision. Use total seconds divided by 86,400 if fractional elapsed days are required.
- Pagination, query-volume optimization and concurrent submission load tests are not implemented; numbering reconciles existing numbers on every new submission. Suitable for a small demo, not yet demonstrated at faculty-wide load.
- The demo seeder preserves existing usable passwords, but resets an explicitly unusable password and forces certain authority activation states on rerun. Restrict it to disposable demo databases or preserve those administrative decisions.
- Audit IP capture trusts forwarded headers without a configured trusted-proxy policy. Configure that policy for deployment.
- Rejected-case reconsideration is not available. Coordinator-only reopening with a recorded reason is a possible enhancement, not an explicit initial-release acceptance requirement.

### 9. Deployment and delivery work

A real secret key, HTTPS, secure cookies, disabled debug, approved hosting, user pilot testing, training and retention decisions are pending. No deployment was performed. The university SSO protocol is unspecified; local accounts satisfy the current login implementation. Multilingual UI, QR codes, satisfaction ratings, escalation rules and SMS/WhatsApp remain optional/future items in the proposal.
